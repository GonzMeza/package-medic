# PackageMedic 0.6 architecture

PackageMedic 0.6 turns dependency comparisons into verified dependency experiments. The release extends the read-only restore and graph engine with opt-in build and test verification, deterministic CycloneDX output, and portable unsigned evidence.

This document is the implementation boundary for 0.6. Features that weaken these invariants must be deferred rather than added as exceptions.

## Product boundary

PackageMedic may answer four separate questions:

1. Did both dependency graphs restore and analyze completely?
2. Did the candidate introduce a dependency-policy rejection?
3. Did the candidate introduce a build or test regression relative to a usable baseline?
4. What dependency and verification evidence can be exported for an immutable source revision?

Passing a repository's selected tests is evidence for the recorded execution context. It is not a claim of general runtime compatibility, complete test coverage, safe package behavior, or release-artifact provenance.

PackageMedic 0.6 does not modify dependencies, accept arbitrary shell fragments, open pull requests, sign evidence, manage signing keys, publish packages, or claim SLSA build provenance.

## Dependency direction

```text
GitHub Action -> PackageMedic.Cli -> PackageMedic.Core workflows
                                      |-- analysis and graph engine
                                      |-- verification engine
                                      |-- execution backends
                                      `-- evidence serializers
```

`PackageMedic.Cli` owns argument parsing, terminal output, atomic output selection, and exit-code mapping. It must not contain build/test state machines or supply-chain serialization logic.

`PackageMedic.Core` remains the internal product engine for 0.6. It is not yet a supported public library API. New implementation is grouped by responsibility without a high-risk assembly split:

```text
Workflows/       comparison and experiment coordinators
Verification/    plans, stage evidence, runners, comparison, verdicts
Execution/       host and optional container execution boundaries
SupplyChain/     CycloneDX, in-toto statements, evidence manifests
```

## Verification levels

The public model has one ordered level:

```text
restore < build < test
```

- `restore` preserves the 0.5 behavior.
- `build` implies restore.
- `test` implies restore and build.
- Unrequested stages are `notRequested`, never `passed`.
- Configuration cannot enable executable verification. The caller must opt in through the CLI or workflow.

The preferred CLI surface is `--verify restore|build|test`. Boolean aliases may only be added as compatibility shims and must normalize to the ordered level before execution.

## Snapshot and policy model

Simulation uses two independently materialized snapshots of the same clean `HEAD`. Only the candidate snapshot receives the exact guarded dependency mutation.

Verified Git diff uses independent snapshots for the immutable base commit and clean current `HEAD`. Plain unverified diff may retain the 0.5 working-tree behavior, but build/test evidence is never attached to mutable input.

Baseline and candidate have separate:

- NuGet global packages folders;
- HTTP and plugin caches;
- CLI homes and application-data roots;
- temporary directories;
- build outputs;
- test result roots; and
- process environments.

The two sides execute sequentially by default. This avoids resource contention and test interference and makes regression attribution conservative.

For pull-request comparison, executable capability and effective gate policy come from trusted workflow inputs and the base revision. Candidate-controlled configuration may be analyzed and reported, but it cannot enable execution or weaken the policy evaluating that same candidate.

## Execution stages

Every stage produces bounded structured evidence with one status:

- `notRequested`: outside the selected verification level;
- `passed`: completed successfully;
- `failed`: completed and produced attributable rejection evidence;
- `incomplete`: could not produce a reliable comparison.

Stage evidence records stable target identities, bounded sanitized failures, and the execution context needed to interpret the result. Durations, machine paths, temporary locations, process IDs, and runner-generated timestamps are operational metadata and do not participate in deterministic comparisons.

### Restore

Restore remains the existing PackageMedic analysis prerequisite. A deterministic candidate restore conflict may reject a simulation. Authentication, availability, timeout, truncation, evaluation, cleanup, and unknown failures remain incomplete.

Restore and MSBuild evaluation receive the same explicit verification configuration later used by build and tests. A multi-target restore is deterministic only when every rejected target has the same recognized, structured NuGet cause; mixed or unclassified failures remain incomplete.

### Build

PackageMedic generates `dotnet build` arguments. It never accepts an arbitrary command string.

- Targets come from the already bounded discovery plan.
- A single solution is built first; projects omitted from it are built separately.
- Build uses `--no-restore`, an explicit configuration, bounded output, a timeout, and process-tree cancellation.
- The original checkout is never a build working directory for verified comparison.

### Tests

PackageMedic generates `dotnet test --no-build --no-restore` arguments and supports separate VSTest and Microsoft Testing Platform adapters. It never installs a reporter package or edits a test project to obtain structured output.

Native Microsoft Testing Platform selection requires a .NET 10 or newer SDK and an effective `global.json` whose `test.runner` is `Microsoft.Testing.Platform`. On earlier SDKs, MTP-compatible projects use the VSTest bridge. GitHub Action callers that require native MTP must select a compatible SDK through `dotnet-version`.

Complete native MTP evidence also requires the repository to provide the `Microsoft.Testing.Extensions.TrxReport` extension. If the extension is absent or does not produce a bounded TRX report, PackageMedic returns an incomplete verdict and never treats process exit code alone as proof that tests passed.

TRX input is read from an owned results root with limits on files, bytes, XML depth, test count, and retained failed-test details. DTDs and external entities are prohibited. Unsupported or malformed required evidence is incomplete, not a passing result.

No automatic retry is performed in 0.6 because retrying can hide flaky regressions. Repositories with no selected tests cannot satisfy a requested `test` verification level.

## Verdict rules

Verdicts are pure output of stage evidence and the dependency comparison:

| Condition | Verdict | Exit |
| --- | --- | --- |
| Requested stages pass and policy passes | `pass` | `0` |
| Exact request produces no observed dependency change | `noChange` | `0` |
| Baseline passes and candidate introduces policy/build/test failure | `reject` | `1` |
| Baseline is unusable or execution/evidence is unreliable | `incomplete` | `2` |

A failure on both sides is not evidence that the candidate is safe or that it introduced the failure. An unusable baseline therefore dominates as `incomplete`.

## Execution security

Restore, MSBuild targets, source generators, analyzers, test adapters, and test code can execute repository-controlled code. Build and test are disabled by default and are not described as safe inspection.

Host execution:

- is intended for local trusted repositories and ephemeral GitHub-hosted pull-request runners;
- rejects `pull_request_target` verification;
- rejects repository- or snapshot-local executable shadowing;
- inherits only the explicit environment boundary;
- exposes no signing, deployment, cloud, or package-publishing credentials; and
- requires an additional explicit authorization on self-hosted runners.

Container execution, when implemented, is a separate backend and never a fallback:

- digest-qualified preapproved image;
- no implicit image pull;
- no privileged mode or container-engine socket mount;
- non-root user and bounded CPU, memory, process, storage, and time;
- network allowed only for the restore phase when explicitly required;
- network disabled for build and tests; and
- unsupported host-specific project shapes return `incomplete`.

## Evidence contracts

Product version and document schemas remain independent.

| Contract | Version in 0.6 |
| --- | --- |
| Scan report | `1` |
| Git diff comparison | `3` |
| Dependency simulation | `2` |
| Configuration | accepts `1`, emits latest supported form |
| Evidence manifest | `1` |
| CycloneDX JSON | `1.7` |
| in-toto Statement | `v1` |

Schema changes are additive where possible. Consumers must be able to distinguish unrequested, failed, and incomplete stages without parsing human messages.

CycloneDX output describes only the resolved NuGet contexts PackageMedic observed. It must use Package URLs, deterministic ordering, credential-free sources, and explicit composition completeness. Missing graph edges are never invented.

PackageMedic emits unsigned in-toto-compatible statements for immutable subjects. External CI may sign them. Hypothetical simulation candidates are not represented as attestations for the checked-out commit and remain excluded from SARIF and Code Scanning.

## Large-repository behavior

- Discovery and MSBuild evaluation results are reused within one side.
- Restore runs once per side; build uses `--no-restore`; tests use `--no-build --no-restore`.
- Worker counts are bounded by existing parallelism policy.
- Subprocess output is streamed/bounded.
- TRX is parsed incrementally.
- Only a bounded number of failure details is retained while totals remain accurate.
- Baseline and candidate caches are never shared for performance.

## Release gates

PackageMedic 0.6 cannot be frozen until tests demonstrate:

- baseline-pass/candidate-build-fail and baseline-pass/candidate-test-fail attribution;
- unusable baseline, timeout, cancellation, truncation, malformed TRX, and cleanup as incomplete;
- VSTest and Microsoft Testing Platform behavior;
- no writes to the original checkout, including cancellation paths;
- policy cannot be enabled or weakened by the candidate revision;
- hostile paths, links, XML, output, environment values, and executable shadowing fail closed;
- deterministic reports and SBOM bytes across different clone paths;
- bounded behavior for large graphs and high-cardinality test results; and
- Windows, Linux, macOS, and supported .NET SDK coverage.
